# MOD003 — Infraestructura de pruebas y CI

**Bloque:** 1 — Fundación ejecutable  
**Rama:** `mod003`  
**Base:** `develop` con `mod002` integrada  
**Dependencias:** web, API y migraciones ejecutables  
**Estado:** Planificada  

## Objetivo

Convertir los controles iniciales en una barrera de calidad real para todos los MRs posteriores.

## Alcance

- Configurar Vitest en web, API y paquetes que contengan lógica.
- Configurar Testing Library para componentes React.
- Configurar Playwright en `tests/e2e`.
- Incorporar axe para verificaciones de accesibilidad automatizadas.
- Crear utilidades para levantar una aplicación Fastify aislada.
- Crear helpers para PostgreSQL de integración con datos efímeros.
- Actualizar GitHub Actions para ejecutar instalación, formato, lint, typecheck, unit tests, integration tests y builds.
- Ejecutar CI en MRs hacia `develop` y `main`, y en pushes a ambas ramas permanentes.
- Añadir PostgreSQL como service container del job de integración.
- Publicar reportes de Playwright únicamente cuando exista una falla.

## Suite mínima

- web: render de la página técnica;
- API: healthchecks y error de validación;
- database: migración sobre base vacía;
- E2E: apertura de la web y consulta del healthcheck;
- accesibilidad: página técnica sin violaciones críticas.

## Reglas

- Las pruebas no dependerán del orden de ejecución.
- No se utilizará la base local del desarrollador desde CI.
- Cada suite deberá limpiar sus datos.
- Los temporizadores y fuentes aleatorias serán controlables.
- No se aceptarán snapshots masivos como sustituto de aserciones funcionales.
- El pipeline fallará ante formato, lint, tipos, pruebas o build inválidos.

## Pruebas y verificaciones

- ejecución local de cada script raíz;
- ejecución del pipeline completo en GitHub Actions;
- prueba deliberada de una falla para verificar que CI bloquea;
- prueba de instalación con cache vacío;
- ejecución repetida de integración para detectar contaminación de datos.

## Fuera de alcance

- cobertura porcentual obligatoria global;
- pruebas visuales completas;
- Lighthouse;
- escaneo de imágenes Docker;
- pruebas de carga.

## Criterios de aceptación

- [ ] Todo MR hacia `develop` ejecuta el pipeline completo.
- [ ] CI utiliza Node.js y pnpm fijados por el repositorio.
- [ ] PostgreSQL de CI inicia, migra y se limpia automáticamente.
- [ ] Playwright puede arrancar web y API sin pasos manuales.
- [ ] Una falla en cualquier control impide aprobar el pipeline.
- [ ] El tiempo de CI inicial se mantiene razonable para el tamaño del proyecto.
- [ ] El Bloque 1 puede reproducirse desde un checkout limpio.

## Condición del MR

La integración de `mod003` cierra el Bloque 1. No se iniciará el sistema visual hasta comprobar un pipeline verde desde cero.

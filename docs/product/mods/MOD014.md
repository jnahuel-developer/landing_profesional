# MOD014 — Sesiones demo

**Bloque:** 5 — Plataforma base del laboratorio  
**Rama:** `mod014`  
**Base:** `develop` con el Bloque 4 cerrado  
**Dependencias:** PostgreSQL, contratos y analítica operativos  
**Estado:** Planificada  

## Objetivo

Implementar sesiones anónimas, aisladas, reiniciables y descartables para todas las demostraciones futuras.

## Alcance

- Crear tablas de sesión y progreso común en `demo_core`.
- Implementar creación, consulta, reinicio y expiración.
- Establecer duración absoluta de una hora desde la creación.
- Emitir un token opaco en cookie segura.
- Generar una semilla estable por sesión.
- Persistir demo seleccionada, rol, escenario, idioma, tema y progreso común.
- Rechazar operaciones sobre sesiones vencidas.
- Implementar comando diario de limpieza de sesiones y datos demo vencidos.
- Permitir reiniciar datos funcionales sin borrar métricas permanentes.
- Añadir eventos analíticos categóricos de inicio, reinicio y expiración.

## Endpoints mínimos

- `POST /api/v1/demo-sessions`;
- `GET /api/v1/demo-sessions/current`;
- `POST /api/v1/demo-sessions/current/reset`;
- `DELETE /api/v1/demo-sessions/current`.

## Reglas

- La expiración no se extenderá por actividad.
- Un visitante no necesitará cuenta ni correo.
- Toda consulta funcional futura deberá incluir scope de sesión.
- Reiniciar conservará el identificador analítico, pero reemplazará el estado demo.
- La limpieza jamás afectará el esquema `platform`.
- No se respaldarán datos de `demo_core`.
- Las fechas del servidor serán la fuente de verdad para expiración.

## Pruebas y verificaciones

- creación y reutilización dentro de la hora;
- expiración con reloj controlado;
- recarga del navegador;
- aislamiento entre dos clientes;
- reinicio y nueva semilla cuando corresponda;
- rechazo de token inexistente o alterado;
- limpieza selectiva;
- preservación de métricas permanentes.

## Fuera de alcance

- datos funcionales de ACME;
- roles concretos de las empresas;
- WebSocket o SSE;
- autenticación de visitantes;
- sesiones superiores a una hora.

## Criterios de aceptación

- [ ] Cada navegador obtiene una sesión opaca y aislada.
- [ ] La sesión vence exactamente una hora después de su creación.
- [ ] Una recarga recupera el estado común vigente.
- [ ] Reiniciar no afecta sesiones ajenas ni métricas permanentes.
- [ ] La limpieza elimina exclusivamente datos descartables vencidos.
- [ ] La API nunca acepta un `sessionId` arbitrario como sustituto de la cookie.

## Condición del MR

El MR deberá incluir pruebas con múltiples clientes y una comprobación explícita de que la limpieza no toca `platform`.

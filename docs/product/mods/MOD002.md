# MOD002 — API, PostgreSQL y migración inicial

**Bloque:** 1 — Fundación ejecutable  
**Rama:** `mod002`  
**Base:** `develop` con `mod001` integrada  
**Dependencias:** PostgreSQL 18 local saludable  
**Estado:** Planificada  

## Objetivo

Establecer la base de backend y persistencia: composición modular de Fastify, contratos compartidos, conexión Drizzle y primera migración versionada.

## Alcance

- Implementar `packages/contracts` con TypeBox, tipos comunes y formato de error.
- Configurar `packages/database` con Drizzle ORM, driver PostgreSQL y Drizzle Kit.
- Crear una migración SQL que declare los esquemas `platform`, `demo_core`, `acme_cafe` y `acme_logistica`.
- Implementar cliente de base de datos con ciclo de vida controlado.
- Crear `app.ts` independiente de `server.ts` para permitir pruebas sin abrir un puerto.
- Registrar Pino, OpenAPI, manejo de errores y validación TypeBox.
- Implementar `GET /api/v1/health/live`.
- Implementar `GET /api/v1/health/ready` con comprobación de PostgreSQL.
- Implementar cierre ordenado de servidor y conexiones.
- Completar comandos `db:generate`, `db:migrate`, `db:seed` y `db:studio`.

## Entregables

- primera migración inmutable;
- contratos tipados de healthcheck y error;
- documentación OpenAPI accesible solo en desarrollo;
- plugin de base de datos reutilizable;
- healthchecks con códigos HTTP y respuestas estables;
- semilla técnica mínima o comando de seed idempotente;
- instrucciones para recrear la base local descartable.

## Reglas

- `live` solo comprobará que el proceso puede responder.
- `ready` devolverá error si PostgreSQL no está disponible.
- Las fechas se persistirán en UTC.
- Los identificadores públicos futuros serán opacos.
- `drizzle-kit push` solo podrá utilizarse contra una base local descartable.
- Una migración aplicada no se reescribirá.
- Los esquemas de demos permanecerán vacíos en esta mod.

## Pruebas y verificaciones

- prueba unitaria del formato de error;
- prueba de inyección de la aplicación Fastify;
- prueba de `live` sin base de datos;
- prueba de `ready` con PostgreSQL disponible y no disponible;
- aplicación de migraciones sobre una base vacía;
- segunda ejecución de migraciones sin cambios;
- comprobación de existencia de los cuatro esquemas.

## Fuera de alcance

- tablas funcionales de contactos, analítica o sesiones;
- autenticación;
- datos semilla de ACME;
- endpoints de producto;
- exposición pública de OpenAPI en producción.

## Criterios de aceptación

- [ ] La API puede construirse sin iniciar el listener.
- [ ] Los cuatro esquemas se crean exclusivamente por migración.
- [ ] `health/live` responde aunque PostgreSQL no esté disponible.
- [ ] `health/ready` refleja correctamente la disponibilidad de PostgreSQL.
- [ ] Los errores de validación usan un contrato estable.
- [ ] La conexión se cierra correctamente al terminar el proceso.
- [ ] No existe lógica de ACME en la base ni en la API.

## Condición del MR

El MR debe incluir la migración generada, su revisión SQL y evidencia de aplicación sobre una base local nueva.

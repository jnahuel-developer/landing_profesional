# MOD010 — Formulario, persistencia y correo

**Bloque:** 4 — Datos permanentes y panel interno  
**Rama:** `mod010`  
**Base:** `develop` con el Bloque 3 cerrado  
**Dependencias:** formulario público y PostgreSQL operativos  
**Estado:** Implementada y verificada localmente

## Objetivo

Convertir el formulario visual en un canal de contacto persistente y confiable, con notificación local mediante Mailpit y una interfaz preparada para Resend en producción.

## Alcance

- Definir contratos TypeBox de envío y respuesta.
- Crear tablas `platform.contacts` y `platform.contact_events` mediante migración.
- Implementar `POST /api/v1/contacts`.
- Persistir antes de intentar la notificación.
- Implementar `MailTransport` con adaptador SMTP para Mailpit.
- Dejar el adaptador Resend encapsulado y activable por configuración, sin requerir credenciales locales.
- Integrar el formulario web con TanStack Query.
- Implementar estados `NEW`, `READ`, `RESPONDED`, `ARCHIVED` y `SPAM`.
- Añadir honeypot, límites de payload y rate limiting por origen técnico.
- Registrar resultado categórico del intento de notificación.

## Modelo mínimo

- identificador opaco;
- nombre;
- correo;
- empresa opcional;
- asunto o categoría cerrada;
- mensaje;
- locale;
- estado;
- fechas de creación y última interacción;
- estado de notificación.

## Reglas

- Un fallo de correo no eliminará ni revertirá el contacto.
- La API no revelará si un correo ya existe.
- El mensaje tendrá límites de longitud y se almacenará como texto, nunca como HTML confiable.
- La respuesta pública no expondrá información interna del transporte.
- No se enviará autorespuesta al visitante en la primera versión.
- Los logs no incluirán mensaje, nombre ni correo completos.

## Pruebas y verificaciones

- envío válido e inválido;
- persistencia antes del correo;
- fallo SMTP con contacto conservado;
- visualización del mensaje en Mailpit;
- honeypot y rate limiting;
- caracteres especiales y payload máximo;
- doble envío desde la interfaz;
- estados accesibles de carga, éxito y error.

## Fuera de alcance

- gestión administrativa de contactos;
- campañas de correo;
- archivos adjuntos;
- CAPTCHA externo;
- automatización comercial.

## Criterios de aceptación

- [x] Un envío válido crea exactamente un contacto.
- [x] El correo local se produce después de confirmar la persistencia.
- [x] La caída de Mailpit no pierde el contacto.
- [x] Los errores son localizados y no filtran datos técnicos.
- [x] Honeypot, límites y rate limiting están activos.
- [x] El formulario funciona con teclado y lector de pantalla.

## Condición del MR

El MR deberá incluir migración, contrato API, evidencia en Mailpit y pruebas del caso de fallo de correo.
